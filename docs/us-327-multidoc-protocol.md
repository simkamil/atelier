# US-327 — Plusieurs documents dans un moteur : contrat de la tranche T0

Tranche T0 (moteur et protocole, sans interface d'onglets). Elle prépare US-327 (onglets, historique, vue et zoom par document, copier-coller entre documents) et le second critère d'US-115 (plusieurs fichiers en argument, chacun dans un onglet). Les onglets et le câblage de `web/app.mjs` sont la tranche suivante ; ce document est son contrat. Il complète [us-203-rich-editor-protocol.md](us-203-rich-editor-protocol.md) (enveloppe ATED v2) et [us-240-format-protocol.md](us-240-format-protocol.md) (mise en forme).

Décisions de l'utilisateur, reprises telles quelles : un seul moteur (un Worker, une instance WASM) avec plusieurs sessions ; le format interne du presse-papiers est un fragment riche gardé en mémoire dans l'application, le presse-papiers système ne reçoit que le texte brut ; au collage, si le texte du presse-papiers correspond au fragment, on colle le fragment riche, sinon le texte.

## 1. Vue d'ensemble

Le moteur garde `RichEditor { sessions: Vec<Session>, … }` (`crates/core-wasm/src/rich_editor.rs`). Une requête désigne son document par l'identifiant de l'enveloppe (`doc_id`, déjà présent dans toutes les trames v2) et ne touche que cette session. Aucun état de session n'est partagé, sauf ce que la section 2.3 liste.

Ce qui ne change pas : les opcodes existants, leur codec, leurs réponses. Un client d'un seul document (l'application actuelle : `docId = 1`, jamais fermé) se comporte comme avant. Ce qui change : `Open` n'écrase plus un autre identifiant ; deux opcodes (fragment) et quatre erreurs s'ajoutent.

## 2. Sessions

### 2.1 `Open`

* Identifiant libre : la session est ajoutée. Identifiant déjà ouvert : **remplacement** de cette session (nouvelle révision 0, historique vide, nouvelle époque d'atlas), comme avant. Choix tranché ainsi parce que l'application actuelle ouvre toujours l'identifiant 1 (`web/rich-editor.mjs`, `docId = 1` ; `web/app.mjs` ne le passe pas, `grep docId web/app.mjs` est vide) et remplace son document à chaque « Ouvrir » ; une erreur sur un identifiant ouvert casserait cette application sans modification. Le front d'onglets attribue des identifiants par compteur monotone, jamais réutilisés pendant la vie de la page : un remplacement involontaire y est impossible.
* La nouvelle session est construite entièrement avant d'être installée : une ouverture refusée (source illisible `RICH_OPEN_FAILED`, limite, mémoire) laisse **toutes** les sessions ouvertes comme elles étaient, y compris celle de l'identifiant remplacé.
* Limite : `MAX_DOCUMENTS = 8` sessions. Au-delà, `RICH_TOO_MANY_DOCUMENTS` (70) ; un remplacement n'augmente pas le nombre.
* Budget mémoire : `MEMORY_BUDGET = 1 Gio`, **estimé** et non mesuré (le WASM ne sait pas rattraper un échec d'allocation : il s'arrête, d'où une estimation prudente avant d'allouer). Poids d'une session : `8 × max(octets de la source, octets du texte à plat) + 2 Mio`, plus `4 ×` les octets de chaque image insérée (`InsertImage`) ou fragment collé (`PasteFragment`). L'ouverture est d'abord refusée sur la seule source (`8 × octets + 2 Mio`, avant l'analyse), puis sur le poids réel. Dépassement : `RICH_MEMORY` (71), aucune session touchée. Un remplacement est jugé sans le poids de la session remplacée. Ordre des refus : limite de nombre, mémoire sur la source, ouverture (`RICH_OPEN_FAILED`), mémoire sur le poids réel.
* Époque d'atlas : `max(dernière époque d'une session fermée ou remplacée, époque remplacée) + 1`. Une époque n'est donc jamais réutilisée pour un même identifiant ; deux documents peuvent porter la même époque sans conflit (le client indexe son atlas par document).

### 2.2 `Close`

Retire la session et libère modèle, historique, `PageCache` (pages mémorisées et atlas), aperçu de style (`Session::preview`, `added_styles`) et mémos. Réponse `Closed`. Un second `Close`, ou toute commande sur l'identifiant, répond `RICH_UNKNOWN_DOCUMENT`. Les polices internées ne sont jamais libérées (voir 2.3) : ce sont des octets `'static` partagés. Le poids de la session est rendu au budget.

### 2.3 Global ou par session

| État | Portée | Détail |
|---|---|---|
| Modèle, historique, révision (relative à l'`Open`), `saved`, `saved_point`, sélection, `typing`, `preferred_x`, `unit_base` | session | |
| `PageCache` (couche, pages, atlas) et `epoch` | session | `Resync` d'un document ne change que son époque |
| `last_command_id` (`DuplicateCommand`), aperçu de style, `added_styles`, `fonts_memo`, `pending`, `resync`, statistiques mémorisées | session | |
| Origine (source DOCX, propriétés, images `(nombre, octets)`), lecture seule | session | |
| Polices internées (`format_char::intern_fonts`, 16 faces et 6 Mio au plus) | global, vie du moteur | `LoadFonts` d'un document les inscrit dans **son** `PageCache` (`add_fonts`) |
| `RichEditor::faces` : les polices données par un `LoadFonts` à un document | global | **un document ouvert ensuite les reçoit à l'`Open`** (`Session::give_fonts`) |
| Documents déjà ouverts au moment d'un `LoadFonts` | session | ne reçoivent pas les polices : ce `LoadFonts` n'est pas rediffusé (recharger les mises en page des autres onglets coûte une mise en page complète chacun). Le client d'un onglet envoie son propre `LoadFonts` quand `ListFonts` lui signale une famille substituée ; les fichiers sont interchangeables (internés une fois) |

| Tampons de l'ABI (`AllocationRegistry`, 64 Mio par tampon, 128 Mio au total) | global | transitoires |

`ListFonts` reste mémorisé par session (`fonts_memo`, invalidé par la révision et par `LoadFonts`).

## 3. Concurrence et équité

Le moteur répond à une trame à la fois, sans interruption possible : l'équité se joue en amont. Constats (lus dans `web/engine-worker.mjs` et `web/rich-editor-client.mjs`) :

* Le Worker garde une file FIFO unique (`MAX_QUEUED_REQUESTS = 32`, 128 Mio) et refuse deux requêtes de même identifiant externe (`DUPLICATE_REQUEST_ID`). Aujourd'hui `createTransport(client)` de `web/rich-editor.mjs` numérote ses requêtes externes à partir de `2n` pour **chaque** éditeur : deux éditeurs sur le même client du moteur produiraient des identifiants identiques. **Un seul transport par client du moteur** : `createEngineTransport(client)` (`web/rich-editor-client.mjs`, nouveau) a un compteur unique ; l'agent des onglets le passe à tous les clients (voir 7.1).
* Chaque `createRichEditorClient` exécute ses commandes une à une et ne pompe la mise en page (`Layout`, `layoutBudget` paragraphes, 16 par défaut, environ 3 ms) que file vide. Il n'y a donc au plus **une requête en vol par document** : une commande de l'onglet actif attend au plus une étape de pompe de chacun des 7 autres documents (`tests/rich-editor-multidoc.mjs` vérifie une borne de 2 pas étrangers avec 4 clients dont un gros document en cours de mise en page ; le double de test, sans latence de Worker, en mesure 0 : la borne du Worker réel, par construction FIFO avec une requête en vol par client, est de 7 pas, soit de l'ordre de 25 ms pour 8 onglets, non mesurée sur un Worker réel).
* Règles pour l'agent des onglets : `layoutBudget` ≤ 64 pour tous les clients (le client monte lui-même à 64 pour un saut de caret de l'onglet actif, `JUMP_LAYOUT_BUDGET`) ; ne jamais passer un budget de 4096 à un onglet d'arrière-plan (700 ms) ; ne pas arrêter la pompe d'un onglet masqué sans raison (`stopPump` vide les pages, `startPump` les redemande à l'affichage) : la pompe de fond est bornée et équitable. La file de 32 suffit : 8 clients ont au plus 8 requêtes en vol, plus les requêtes hors éditeur (fichiers, ABI).
* **Honnêtement : le moteur est monothread.** Une commande longue d'un onglet **bloque l'onglet actif** le temps de son exécution : `Open` d'un gros DOCX (analyse, de l'ordre de la seconde à plusieurs secondes pour 32 Mio), `Save` d'un autre onglet, `CopyFragment` d'une grande plage, `ReplaceAll`, `Statistics`. Aucune parallélisation ni préemption n'est possible dans T0. Règles pour le front : (1) pas d'`Open` d'arrière-plan pendant que l'utilisateur tape : un `Open` part au plus tôt quand la file de l'onglet actif est vide, et il est annoncé (indicateur occupé) ; (2) lancement US-115 avec plusieurs fichiers : ouvertures **séquentielles**, la suivante attend la fin de la précédente et de la mise en page de son premier écran, jamais en parallèle ; (3) un `Save` d'un onglet d'arrière-plan (fermeture) est un travail au premier plan avec indicateur ; (4) aucune requête de pompe de 4096.
* Aucune modification de `web/engine-worker.mjs` : un ordonnanceur à priorités ne serait utile qu'avec plusieurs requêtes en vol par document, ce que le client interdit.
* Une requête annulée côté Worker alors que le moteur l'a déjà exécutée (le moteur est synchrone : l'annulation n'agit qu'avant l'exécution ou sur la réponse) équivaut à une réponse perdue : voir 4.

## 4. Resync, réponse perdue, redémarrage

* `Resync` est par document, idempotent : nouvelle époque d'atlas de ce document, pages invalidées au prochain `State`, fenêtre de texte jointe.
* Réponse perdue côté ABI (`STATUS_LIMIT`, `EDITOR_RESPONSE_LIMIT`, `registry.replace_in_flight` en échec) : `lib.rs` appelle `RichEditor::mark_resync()`. **Corrigé en T0** : il marquait « la session active » ; il marque désormais le document de la **dernière réponse** (`last_doc`, posé à chaque `transact`). Le moteur étant synchrone, c'est exactement le document dont la réponse est perdue. Si cette réponse était un `Close`, la session n'existe plus : sans effet.
* Réponse perdue côté Worker ou transport (requête annulée après exécution) : le client du document passe en `needsResync` (`guarded`) et envoie `Resync` à son prochain tour ; les autres clients n'en savent rien et n'ont rien à faire. Vérifié sur le vrai WASM (`tests/rich-editor-multidoc.mjs`, « lost reply »).
* Annulation : un `Open` annulé alors qu'il a été exécuté laisse une session ouverte que le client croit absente ; le client renvoie `Open` au prochain essai (remplacement : sans erreur de limite ni de doublon) ou `Close`.
* Fermeture pendant une requête en vol : la file du client est ordonnée ; `closeDocument()` passe après les commandes déjà soumises. Une requête d'un autre client en vol n'est pas affectée (autre session). Après `Closed`, toute commande répond `RICH_UNKNOWN_DOCUMENT`.
* **Trap WASM dans le même Worker** (`web/wasm-loader.mjs` : `resetAfterTrap` recrée l'instance, `EngineTrapError`) : le Worker reste vivant mais l'instance est neuve, donc **toutes les sessions sont perdues** ; la requête en vol échoue en `EDITOR_ENGINE_FAILED` (`transport.request` : réponse externe `Failed`), les suivantes en `RICH_UNKNOWN_DOCUMENT`. Si la recréation échoue (`resetError`), le moteur reste inutilisable : même traitement que Worker mort. Reprise du front, dans cet ordre : (a) à la première de ces deux erreurs, **tous** les onglets passent à l'état « perdu » (bandeau, saisie coupée) ; le dernier texte affiché de chaque onglet reste visible mais n'est plus lié à une session ; (b) l'utilisateur choisit par onglet : **rouvrir depuis le fichier** (octets relus par le pont de fichiers ; les modifications non enregistrées sont perdues), **récupérer** (dernier enregistrement de récupération s'il existe), ou **copier le texte affiché** (le front garde la dernière fenêtre de texte `cache.textWindow`, au plus 256 Kio autour du focus : ce n'est pas le document entier, ne pas la présenter comme une sauvegarde) ; (c) un nouvel `Open` du même identifiant reconstruit l'onglet (sans conflit, 2.1). **Worker mort** (`close`, `fatal`, erreur d'initialisation) : le client du moteur est inutilisable ; le front recrée le Worker, le transport (`createEngineTransport`) **et tous les éditeurs** (clients, caches, caches d'images : rien ne se reprend d'un client lié à l'ancien transport), puis rouvre comme ci-dessus.
* Worker redémarré (nouvelle instance WASM) : tous les identifiants sont inconnus. Le front le détecte au premier `RICH_UNKNOWN_DOCUMENT` sur un onglet qu'il croit ouvert, conclut « moteur perdu » pour tous les onglets, et rouvre chacun avec `Open` (même identifiant) à partir de ses derniers octets enregistrés ou de récupération ; les modifications depuis ne sont pas récupérables par le moteur et l'utilisateur en est informé. Vérifié : nouveau client sur un moteur neuf, `RICH_UNKNOWN_DOCUMENT` puis `Open` du même identifiant.
* Open refusé pour limite ou mémoire : seule l'ouverture échoue (`RICH_TOO_MANY_DOCUMENTS`, `RICH_MEMORY`), le client reste `opened === false` (ou, pour un remplacement, rouvre son ancien état par `Resync`, comportement existant du client), les autres sessions sont intactes (testé sur le moteur et sur le client).

## 5. Fragment riche

### 5.1 Commandes

| Opcode | Commande | Corps | Réponse |
|---|---|---|---|
| `0x0170` | `CopyFragment` | `u64` révision, `u64` début, `u64` fin (positions à plat) | `Fragment` (`0x8140`) |
| `0x0171` | `PasteFragment` | `u32` longueur, octets du fragment | `State` |

Plage libre vérifiée : `0x0140` est `MoveText`, `0x0150` à `0x016F` appartiennent à la mise en forme (`LoadFonts` = `0x016F`), `0x0170` à `0x017F` sont réservés au fragment, `0x8140` à `0x814F` aux réponses de fragment (les réponses de mise en forme occupent `0x8130` à `0x813F`).

`Fragment` : `u64` révision, `u32` indicateurs (bit 0 `lossy`, le reste réservé nul), texte (`u32` + UTF-8, au plus 1 Mio), octets du fragment (`u32` + octets, au plus 16 Mio). Côté JS : `{type:"fragment", revision: BigInt, lossy: boolean, text: string, bytes: Uint8Array}` ; la commande décodée est `{type:"copyFragment", revision: BigInt, start: BigInt, end: BigInt}` ou `{type:"pasteFragment", bytes: Uint8Array}`.

Nouveaux codes d'erreur (70 à 79) : `RICH_TOO_MANY_DOCUMENTS` 70, `RICH_MEMORY` 71, `RICH_FRAGMENT_INVALID` 72 (octets qui ne sont pas un fragment lisible), `RICH_EMPTY_SELECTION` 73 (copie d'une plage vide). Taille excessive : `RICH_LIMIT`.

### 5.2 `CopyFragment`

* Garde de révision comme `Search` : une révision différente de la courante répond `RICH_STALE_REVISION`. Positions : mêmes contrôles que `ReplaceRange` (`RICH_POSITION_OUT_OF_RANGE`, `RICH_POSITION_NOT_BOUNDARY`, `RICH_INVALID_RANGE`). Plage vide : `RICH_EMPTY_SELECTION`. Aucun changement d'état, de révision ni d'historique ; permis en lecture seule.
* `text` est ce que `TextWindow` donne pour la même plage (U+FFFC pour chaque objet, saut ou symbole, `\n` entre paragraphes) : c'est la clé de correspondance du collage (voir 5.4). Plus de 1 Mio : `RICH_LIMIT`.
* Contenu du fragment, lu par l'API publique du modèle (`LayoutContext::paragraph`, `block_kind`, `catalog`) : par paragraphe touché, le texte de la portion sélectionnée, les propriétés de paragraphe directes, les segments de caractères (`CharRun` rognés à la plage) avec leurs attributs directs, les images (`IMAGE_OBJECT_KIND` : octets autonomes), les sauts (ligne, page, colonne, habillage), les symboles, les champs entièrement inclus, les liens (rognés) ; les styles référencés (paragraphe et caractère) avec leur chaîne `based_on`, définition comprise. Le dernier paragraphe est « ouvert » : s'il est vide (la sélection se termine juste après une marque de paragraphe) il porte seulement les propriétés de ce paragraphe.
* Non transporté, signalé `lossy` : les blocs opaques (omis) ; les tableaux (leurs paragraphes de cellule sont copiés comme paragraphes ordinaires, la structure est perdue) ; les objets d'ancrage autres que les images (formes, graphiques : leur XML renvoie à des relations du paquet source, inutilisables dans un autre document) ; les signets (un nom de signet est unique dans un document). Les liens vers un signet gardent leur cible, qui peut ne pas exister dans le document de destination (comme dans Word).

### 5.3 Format du fragment (version 1)

Petit-boutiste. `"ATFR"`, `u16` version (1), `u16` indicateurs (0) ; `u32` nombre de styles, les styles ; `u32` nombre de paragraphes (au moins 1), les paragraphes. Chaque champ facultatif est un octet 0 ou 1 suivi de sa valeur ; les chaînes sont `u32` + UTF-8 (64 Kio au plus) ; les énumérations sont l'indice dans une table fixe de `rich_editor/fragment.rs`. Un style : identifiant, genre (paragraphe 0, caractère 1), `based_on`, attributs de caractère, police, couleur et surlignage de thème, propriétés de paragraphe (dont la trame `shading` : remplissage, motif, couleur du motif, et les six bordures haut, gauche, bas, droite, entre, barre : style 0 à 4 `None, Single, Double, Dotted, Dashed`, épaisseur en huitièmes de point `u32`, espace `u8`, couleur facultative), nom, `quick`, `ui_priority` (`linked_style` et `is_default` ne sont pas transportés). Un paragraphe : texte, propriétés (mêmes champs que celles d'un style), segments (`début`, `fin`, attributs), images (`offset`, genre, octets, au plus 8 Mio), sauts, symboles, champs, liens.

Version : un fragment de version inconnue est refusé (`RICH_FRAGMENT_INVALID`) ; le fragment ne vit qu'en mémoire de l'application pendant la session (jamais écrit sur disque), les deux côtés sont la même version du moteur : le champ sert aux évolutions. **Évolution du modèle** : `CharAttrs`, `ParaProps` et `Style` sont déstructurés sans `..` dans `fragment.rs` ; un champ ajouté (la trame et les bordures de l'autre tranche en ajoutent peut-être) **arrête la compilation** à l'intégration, à cet endroit, au lieu d'être perdu en silence par un copier-coller (les attributs « opaques » passent déjà tels quels).

Bornes : fragment 16 Mio, texte total 1 Mio, 256 styles, image 8 Mio, 512 images par document et 32 Mio d'images (limites d'`InsertImage`, appliquées au collage : dépassement `RICH_LIMIT`). Décodage : tout est borné par les octets restants (aucune allocation proportionnelle à un compteur non vérifié), les chaînes sont de l'UTF-8 valide, les décalages de segments, d'objets, de champs et de liens sont des frontières de caractère, puis chaque paragraphe passe `Paragraph::validate_local` (frontières de graphème, recouvrements, attributs valides).

### 5.4 `PasteFragment`

* Refusé en lecture seule (`RICH_READ_ONLY`) ; octets invalides `RICH_FRAGMENT_INVALID` ; mémoire `RICH_MEMORY` (`4 ×` la taille). Les erreurs ne changent ni le document, ni l'historique, ni la révision.
* Remplace la sélection courante de la session (une sélection non vide est supprimée, comme `InsertText`), en **une seule étape d'annulation, une seule révision** : `RichDocument::replace_with_paragraphs` (nouveau, `crates/text-model/src/rich/edit/paste.rs`) applique un `replace_range` du texte puis un second élément d'historique (segments, propriétés, éléments en ligne) groupé avec le premier (même mécanisme que `replace_ranges`). `Ctrl+Z` rend le document identique (testé sur le texte, les paragraphes et la validation du modèle) et `Ctrl+Y` recolle.
* Règles de paragraphe : le premier morceau s'ajoute au paragraphe du point d'insertion, qui garde ses propriétés — sauf s'il est vide et que rien n'est remplacé (il prend celles du morceau, règle de Word). Les autres morceaux deviennent des paragraphes avec leurs propres propriétés ; le dernier, s'il est vide, laisse la fin du paragraphe coupé dans son propre paragraphe aux propriétés d'origine. Les caractères prennent exactement les attributs de la source (`overwrite_runs`), pas ceux du caractère précédent. Un objet ou un saut au tout bord d'un morceau peut se placer avant des éléments déjà là au même décalage (ordre par identifiant) ; le curseur se place après le contenu collé.
* Styles absents du document cible (règle de Word) : un style qui existe dans la cible **sous le même nom (insensible à la casse) et du même genre** est utilisé, quelle que soit sa définition ; sinon il est ajouté avec sa définition (`add_style`, identifiant libre trouvé par suffixe `_2`, `_3`…, `based_on` ré-aiguillé) et inscrit dans `added_styles` : l'enregistrement DOCX l'écrit s'il est utilisé (testé : enregistrer puis rouvrir garde le style et l'image). Le catalogue est hors historique : annuler un collage laisse ses styles définis mais inutilisés (non enregistrés). Un style intégré « latent » absent de la cible est ajouté avec la définition de la source, non avec celle du profil par défaut (écart assumé).
* Document **TXT** (`Profile::Txt`) : texte seul. Les paragraphes sont joints par `\n`, les sauts de ligne deviennent `\n`, les symboles leur caractère ; images et sauts de page sont omis. Passe par `Session::edit` (comme `InsertText`).
* Images : comptées (`origin.images`) ; chaque image garde ses octets et son identité dans la cible (identifiants neufs : `ImageBitmap` d'un document ne vaut que pour lui, voir 7.4).
* Revalidation : les identifiants d'éléments sont frappés par `alloc_id` du document cible (jamais réutilisés) ; un collage refusé en consomme sans effet.

### 5.5 Correspondance texte / fragment (côté application)

Règle : au collage, `sanitizeEditText(clipboardText)` est comparé à `sanitizeEditText(fragment.text)` (`web/rich-editor.mjs` : fins de ligne ramenées à `\n`, U+FFFC et contrôles supprimés — c'est ce qui absorbe le `\r\n` de Windows). Égaux : `pasteFragment(fragment.bytes)` ; différents ou aucun fragment : `insertText(sanitizeEditText(texte))`. Le fragment est un état d'application (un seul, remplacé à chaque copie, indépendant des onglets : il survit à la fermeture de l'onglet source parce que ses octets sont des copies). Il doit être invalidé quand le texte du presse-papiers cesse de lui correspondre (comparaison à chaque collage, pas de détection d'événement). Détail à connaître : la copie du navigateur est **synchrone** (`event.clipboardData.setData` dans `copy`), alors que `CopyFragment` passe par le Worker ; l'application écrit donc le texte tout de suite (`getClipboardSnapshot`, existant) et demande le fragment juste après ; un collage qui arrive avant la réponse attend la promesse en cours (ou colle le texte, dégradation sans perte de texte).

## 7. Simulation écrite des consommateurs

Méthode : pour chaque consommateur, la donnée ou la fonction réellement utilisée (lue dans le code, non supposée), le comportement attendu pendant la tranche suivante, puis les chemins d'erreur : réponse perdue, annulation, `Resync`, fermeture en vol, ouverture refusée, Worker redémarré.

### 7.1 `web/app.mjs` actuel (doit marcher sans modification pendant T0)

Lu : `createRichEditor({...})` sans `docId` (donc 1) à `app.mjs:389` ; `editor.openDocument(source)` aux lignes 417, 503, 551 ; lancement US-115 (ligne 417 : premier fichier ouvert, suivants comptés) ; onglet Fichier : `fileTab.attach({ host, openDocument })`. ### 7.2 Front d'onglets (tranche suivante)

* **Créer** : `docId = ++compteur` (jamais 0, jamais réutilisé) ; un `createRichEditor` (client, cache, cache d'images, zoom, origine) par onglet sur le **même transport** (7.3). `open` refusé par le moteur (`RICH_TOO_MANY_DOCUMENTS`, `RICH_MEMORY`, `RICH_OPEN_FAILED`) : l'onglet n'est pas créé, message distinct par code, les autres onglets intacts (testé : neuvième ouverture refusée, `opened === false`, puis une place libérée la rend possible). **Open échoué sans code `RICH_*`** (`CLIENT_TRANSPORT` : réponse perdue ou requête annulée **après** exécution, `EDITOR_ENGINE_FAILED`) : le moteur peut avoir installé la session sans que le client le sache ; le front envoie alors, au mieux, un `Close` du même identifiant (`RICH_UNKNOWN_DOCUMENT` = déjà absent, sans suite) avant de supprimer l'onglet, pour qu'une session fantôme ne compte pas dans la limite de 8. Si ce `Close` échoue lui-même (transport mort), l'identifiant reste réservé dans le compteur et le front avertit que le moteur est instable (4).
* **Fermer un document, API** : `editor.closeDocument()` **n'existe pas** aujourd'hui (`rich-editor.mjs` ne l'expose pas ; `dispose()` fait `abort`, retire les écouteurs et `rich.dispose()`, il **n'envoie pas** `Close`). À ajouter (agent des onglets) : `async editor.closeDocument()` = `rich.closeDocument()` (`Close`, réponse `Closed`, `cache.reset()`, pompe arrêtée) puis `images.clear()`, surcouche des marques et fenêtre de texte vidées ; elle résout aussi sur `RICH_UNKNOWN_DOCUMENT` (comportement de `closeExchange`). `editor.dispose()` doit être **précédé** de `closeDocument()` (ou l'inclure, en meilleur effort, borné) : libérer le DOM sans fermer la session laisse la session dans le moteur et dans le budget. Ordre de fermeture d'un onglet : confirmation/enregistrement, `closeDocument()`, `dispose()`, retrait du DOM. Alternative acceptable : exposer le client (`editor.client`) ; le contrat moteur est le même.
* **Basculer** : aucune commande moteur. Chaque onglet garde son `EditorPageCache`, sa vue, son zoom, sa sélection et son historique moteur. Voir 7.9 pour le DOM, la suspension et le filtrage des callbacks, 7.5 pour la mise en forme.
* **Fermer avec demande d'enregistrement** : « modifié » est le `dirty` du dernier `State` de l'onglet (faux après `MarkSaved` ou retour de l'historique au point enregistré). Dialogue (Enregistrer / Ne pas enregistrer / Annuler) puis `Save` (`SaveData`), écriture par le pont de fichiers, `MarkSaved(revision)` (`RICH_STALE_REVISION` si le document a bougé : redemander), puis fermeture. Fermeture en vol : la file du client est ordonnée, `closeDocument()` passe après les commandes déjà soumises.
* **Réordonner** : purement front. **Fermer tout** : `closeDocument()` de chaque onglet, ou rien (la fin du Worker libère tout). **Dernier onglet fermé** : le front ouvre un `Open` vide (l'application suppose un document actif ; ce n'est pas une règle moteur).
* Moteur perdu : voir 4.

### 7.3 `rich-editor.mjs` / `rich-editor-client.mjs` / `engine-worker.mjs` / transport

Réels : le client numérote ses requêtes internes (`nextRequestId`, par client, 1 à 2^32-1) et vérifie `docId` et `requestId` de la réponse : aucune collision entre documents. Le transport externe est le point commun : `createTransport` de `rich-editor.mjs` (compteur `outer` privé, début `2n`) **ne doit plus être créé par éditeur** — il faut une option `transport` de `createRichEditor` (changement de `rich-editor.mjs`, tranche suivante) ou `createEngineTransport` en dehors. `engine-worker.mjs` : `jobsById` rejette les doublons d'identifiant externe, `queue` FIFO de 32. Chemins d'erreur : `guarded` → `needsResync` sur échec de transport ; `closeExchange` ; `open` refusé ; tous par document, tous éprouvés sur trois à huit clients (test node).

### 7.4 `EditorPageCache`, `rich-image-cache`, atlas, miroir accessible

* `EditorPageCache` : un par client (par document), époque d'atlas propre (`atlasEpoch`) ; deux documents peuvent partager une valeur d'époque sans effet. Testé : trois clients, trois époques distinctes, un `Resync` n'en change qu'une.
* `rich-image-cache` : clé = identité d'objet (`NodeId::value`, `imageId` des listes d'affichage). **Cette identité est locale au document** (`atelier_model::NodeId` : « deux arbres peuvent émettre des valeurs égales »). Un cache d'images **par document** (ce que fait déjà `createRichEditor`, une instance par éditeur) est obligatoire ; un cache partagé entre onglets mélangerait les images. `images.clear()` à chaque changement d'époque reste par éditeur. Un collage d'image crée des identités neuves dans la cible.
* Miroir accessible (`accessibleWindow`) : par client, par document, révision en garde ; inchangé. Au changement d'onglet le miroir est reconstruit depuis le client de l'onglet affiché.

Séquence de bascule A vers B, dans cet ordre : (1) **annuler l'aperçu de style de A** : `previewStyle({ show:false })` via `controller.client` de A (sinon l'aperçu reste affiché dans A, sans effet sur son document, jusqu'à sa prochaine commande) et attendre la réponse ; (2) `paraFormat.detachEditor()` ; (3) `formatController.detach()` ; (4) `setSuspended(true)` et `setVisible(false)` sur A (7.9) ; (5) `formatController.attach(B)`, `paraFormat.attachEditor(B, { canvas, scrollport, spacer })` de B ; `formatKeys` cible `() => active.element` et `isEnabled: () => Boolean(active.canEdit)` (des fonctions déjà : se rebrancher sans recréer) ; (6) `setSuspended(false)` sur B. Les modules à état propre (`charFormat`, `stylesPane`) lisent `controller.client`/`snapshot` : rien à recréer. `last_command_id` : par session, le compteur du front est par éditeur. `format-char` / `LoadFonts` : un `LoadFonts` par document utilisateur de la famille (2.3) ; budget global 16 faces, 6 Mio ; un échec n'affecte que sa commande.

### 7.6 Recherche et remplacement, statistiques, propriétés

`Search`, `SearchRects`, `Replace`, `ReplaceAll`, `Statistics`, `PropertiesRead/Apply` : tous par session, gardés par la révision du document visé ; aucun état moteur partagé (vérifié : seuls statics du moteur riche : `LOADED_FONTS` et les registres de l'ABI). Au changement d'onglet le front **ferme ou recalcule** le panneau de recherche pour l'onglet affiché (les occurrences sont par révision et par document) ; un `Replace` sur un onglet ne peut pas viser un autre document (l'identifiant est dans la trame). Statistiques et propriétés : lues pour l'onglet affiché.

### 7.7 Onglet Fichier (récents, modèles), lancement US-115, enregistrement

* Récents et modèles : ouvrent dans un **nouvel onglet** (`Open` d'un nouvel identifiant) au lieu de remplacer ; le front choisit (ouvrir dans l'onglet courant s'il est vide et non modifié). Refus de limite : message, le fichier reste dans la liste.
* Lancement avec plusieurs fichiers : le pont `launch` (`FileRuntime.launch`, borné à 16 chemins, lu dans `docs/us-115-single-instance.md`) livre les fichiers un par un (`ok|…` ou `ok|` si rien n'attend). Chaque fichier `.txt`/`.docx` devient un onglet (`Open`) ; le premier qui reçoit `RICH_TOO_MANY_DOCUMENTS` arrête la boucle, le front signale « n fichiers non ouverts (8 onglets au plus) » (clé i18n à ajouter) ; `RICH_MEMORY` : message de mémoire. `.docx` avec aperçu : le chemin existant (`import_docx_for_editor`, hors session riche) reste.
* Enregistrement : `Save` est par document, `MarkSaved` par document ; deux onglets peuvent enregistrer en même temps (requêtes distinctes, une à la fois dans le moteur). Un onglet « Enregistrer sous » ne change que le nom de cet onglet. Les octets d'un `SaveData` d'un document ne dépendent que de cette session (les styles collés sont écrits par `added_styles`).

### 7.8 Glisser-déposer de texte entre documents, copier, couper, coller

* Dans un même document : `MoveText` (inchangé). **Entre onglets** : le glisser vers un autre onglet n'existe pas physiquement (un seul canvas visible) sauf glisser sur la barre d'onglets ; si le front le permet : déposer = `copyFragment(source)` puis `setSelection(point de dépôt)` puis `pasteFragment` sur la cible ; déplacer = ensuite `replaceRange(début, fin, "")` sur la source, seulement si la révision de la source est encore celle du fragment (`CopyFragment` porte la garde). Deux documents, deux étapes d'annulation distinctes (une par historique) : à documenter dans l'interface.
* Copier : texte du presse-papiers écrit sans attente (synchrone), `copyFragment` demandé ensuite. Couper : copie puis `deleteSelection` (`text-input` existant). Coller : règle 5.5. Un fragment trop gros (`RICH_LIMIT`) ou une plage vide (`RICH_EMPTY_SELECTION`) : le texte seul est copié, l'application oublie le fragment précédent (sinon un ancien fragment resterait associé à un texte égal : la comparaison l'écarterait quand même).
* Perte de réponse pendant `pasteFragment` : le client resynchronise ; le texte du presse-papiers égal au fragment, une nouvelle tentative recolle le même contenu (pas d'idempotence : si la première avait été appliquée, le contenu est doublé ; le front compare `cache.revision` avant et après la reprise, comme `insertText`). Annulation d'un collage en cours : même chemin (réponse perdue).

### 7.9 DOM, suspension, callbacks, hôte et fermeture de fenêtre

* **DOM par onglet** : `canvas`, `scrollport`, `spacer`, `mirrorContainer` (miroir accessible) et le champ de saisie caché (`attachTextInput`, ajouté à `document.body` par éditeur) sont créés **par onglet** ; un seul est visible (`hidden` sur les autres, `aria-hidden`). `createRichEditor` exige ces éléments.
* **Suspension, ce qui existe** : `editor.setSuspended(v)` est `setBusy(v)` (`rich-editor.mjs:1166`) : coupe la saisie (`input.element.disabled`), annule la sélection à la souris et le glisser, notifie `onBusy` et `subscribe("busy")`. Il **n'arrête pas** le clignotement du curseur (`setInterval` de 530 ms qui repeint la surcouche), ni la pompe, ni les écouteurs de redimensionnement et de défilement. À ajouter (agent des onglets) : `setVisible(false)` qui coupe le clignotement, ne rend plus (`renderer.render`), ignore le `ResizeObserver`, vide la surcouche des marques et libère le focus. La **pompe de fond continue** (équitable, 3) : l'arrêter vide les pages, qui sont redemandées à l'affichage.
* **Callbacks** `onState`, `onZoom`, `onViewport`, `onReadOnly`, `onBusy`, `onImages`, `onError` : chaque éditeur reçoit des callbacks **filtrés** (`if (tab === active) ui(...)`) ; l'erreur d'un onglet caché est mise en file et signalée sur l'onglet (pastille), pas par une boîte modale sur un autre document. `documentStatus`, `zoomControls`, statistiques, état « modifié » du ruban : relus depuis l'éditeur actif à la bascule.
* **`createReaderModeToggle` et `formatKeys`** (`app.mjs:398-400`) : le bouton lit `editor.input` ; il est rebranché sur l'éditeur actif à chaque bascule (le mode lecteur est une préférence globale : l'appliquer à chaque éditeur par `screenReaderMode`/`onScreenReaderMode`). `formatKeys` cible `() => active.element`.
* **État « modifié » de la fenêtre** : `host.notifyDirty(dirty)` est **partagé** : appelé par `rich-editor.mjs:488-492` à chaque changement du `dirty` de **son** éditeur, envoyé tel quel au natif (`native-host.mjs:325`, message `dirty|1|0` ; le natif ne garde qu'un booléen, `win32.rs:486`). Avec plusieurs onglets, chaque éditeur reçoit **son propre hôte d'onglet** (même forme que l'hôte natif ; `pickOpen`, `readTicket`, etc. délégués) dont `notifyDirty` mémorise le booléen de l'onglet et appelle le vrai `host.notifyDirty(OU de tous les onglets)` **seulement quand le OU change**. Fermer un onglet retire sa contribution (et ré-émet si le OU change). **Fermeture de la fenêtre** : sur `WM_CLOSE` le natif affiche sa propre confirmation unique (`win32.rs:1300-1310`), il **ne peut pas** demander l'enregistrement onglet par onglet. Une demande par onglet exige un message natif nouveau (« fermeture demandée » vers le front, qui parcourt les onglets modifiés) : hors T0, à demander à l'agent natif ; sans cela le comportement est une confirmation globale dès qu'un onglet est modifié.

## 9. Limites connues

* `Session::weight` est une **borne haute posée à l'ouverture** (8 × max(source, texte) + 2 Mio) à laquelle s'ajoutent 4 × les octets de chaque image insérée et de chaque fragment collé **réussi** ; elle n'est **jamais recalculée ni décrémentée** (supprimer du texte ou annuler un collage ne rend rien au budget ; seule la fermeture ou le remplacement de la session le rend). Elle n'a pas de rapport exact avec la mémoire réelle.
* Un collage refusé après l'import des styles (par exemple `RICH_LIMIT` d'images) **laisse les styles importés définis mais inutilisés** : assumé (le catalogue est hors historique, 5.4) ; ils ne sont pas enregistrés tant qu'aucun paragraphe ne les utilise.
* Décodage du fragment : aucune allocation proportionnelle à un compteur (les `Vec` partent de `min(compteur, 1024)`) ; un fragment de 4 Mo qui déclare 4 000 000 paragraphes est refusé sans croissance de mémoire (test sur le vrai WASM).
* Poids mémoire estimé, non mesuré ; un document dont l'analyse produit bien plus de 8 fois sa source peut dépasser le budget réel sans être refusé.
* Tableaux et blocs opaques ne passent pas (signalé), objets autres qu'images non plus ; signets non transportés.
* Les polices chargées après l'ouverture d'un autre onglet ne lui sont pas rediffusées.
* Un style intégré latent absent est ajouté avec la définition de la source.
* L'ordre d'un objet et d'éléments déjà posés au même décalage, en bord de collage, peut différer de l'ordre de la source.
* Collage depuis un autre moteur (autre instance du Worker) : non prévu ; le fragment ne vit que pendant la session.

## 10. Front d'onglets (livré par US-327)

Ce qui est codé, et les écarts avec les sections 7 et 8 (le contrat dit quoi, ceci dit comment) :

* **Fichiers** : `web/document-tabs.mjs` et `.css` (barre), `web/app.mjs` (un éditeur par onglet), `web/rich-editor.mjs` (option `transport`, `closeDocument()`, `setVisible()`, collage riche), `web/format-controller.mjs` (`detach()`), `web/styles-pane.mjs` (`cancelPreview()`), `web/native-host.mjs` et `crates/desktop-win/src/file-bridge.rs` (lancement, voir plus bas), `web/i18n/fr-FR.txt` (bloc US-327). `document-tabs.mjs` et `.css` sont embarqués dans l'exe (`resources.rs`, sondes de `win32.rs`).
* **Barre** : `role="tablist"`, un bouton `role="tab"` par document (`aria-selected`, tabindex itinérant, nom « titre, modifié, erreur »), un bouton Fermer hors de l'ordre de tabulation. Clavier : flèches, Début, Fin, Suppr ; Alt+Maj+flèche gauche ou droite déplace l'onglet ; Ctrl+Tab, Ctrl+Maj+Tab, Ctrl+W et Ctrl+F4 depuis n'importe où dans la fenêtre (sauf dialogue modal). Glisser : pointeur, seuil de 6 px, Échap annule. Pas d'`aria-controls` : le panneau du document affiché (`role="tabpanel"`) porte les identifiants historiques `document-scroll`, `document-canvas`, `page-spacer`, `document-text` (ils passent d'un onglet à l'autre, les tests et les modules les cherchent par là) ; un onglet n'a donc pas d'identifiant de panneau stable.
* **Un éditeur par onglet**, un seul `createEngineTransport`, `docId` par compteur monotone. `createRichEditor({ transport, docId })` ; `editor.setVisible(false)` à la sortie d'un onglet (coupe clignotement, dessin, redimensionnement, mémorise le défilement, libère le focus), `setVisible(true)` après réaffichage du DOM. **La pompe de fond continue** pour un onglet caché (3 : l'arrêter vide les pages). `closeDocument()` envoie `Close` ; `dispose()` envoie `Close` de lui-même (borné à 2 s) si la session est ouverte.
* **Bascule** (7.5) : `switchTo()` annule l'aperçu de style (`stylesPane.cancelPreview()`, réponse attendue), détache la surcouche des marques et le contrôleur de mise en forme, suspend et cache l'onglet quitté, affiche le nouveau, rattache contrôleur et surcouche, reprend l'onglet, reconstruit le menu contextuel et le bouton du mode lecteur sur l'éditeur affiché, relit état, zoom, barre d'état, propriétés. La recherche, le remplacement et les statistiques parlent à un mandataire de l'éditeur actif ; la recherche est recalculée pour le document affiché. Une bascule demandée pendant une opération (dialogue, ouverture, enregistrement, fermeture) est refusée.
* **Ouvrir** : Nouveau, Ouvrir, Ouvrir DOCX, modèles, récents et fichiers lancés ouvrent un NOUVEL onglet, sauf si le document affiché est un document vierge que personne n'a touché (remplacé, comme Word ; Nouveau n'y ajoute alors rien). Huit documents au plus : `RICH_TOO_MANY_DOCUMENTS` et `RICH_MEMORY` sont annoncés (clés `tabs.error.too_many`, `tabs.error.memory`) sans toucher les autres onglets. Une ouverture refusée ou annulée libère l'onglet créé (`Close` du même identifiant, au mieux). `editor.openDocument` rend `{ kind: "error", key, code }` avec la clé propre à ces deux codes.
* **Fermer** : Ctrl+W, bouton, clic du milieu. Onglet modifié : Enregistrer / Ne pas enregistrer / Annuler (Enregistrer passe par la boîte « Enregistrer sous » du natif ; refus ou annulation : l'onglet reste ouvert). Le dernier onglet fermé fait place à un document vierge. Ordre : confirmation, bascule vers le voisin, retrait de la barre, `closeDocument()`, `dispose()`, retrait du DOM.
* **Hôte agrégé** (7.9) : chaque éditeur a son hôte (`notifyDirty` mémorisé par onglet) ; le natif reçoit le OU, seulement quand il change.
* **Copier-coller** (5.5, 7.8) : le texte part tout de suite dans le presse-papiers, `copyFragment` est demandé juste après (un seul fragment pour l'application, module `rich-editor.mjs`) ; au collage, le texte du presse-papiers comparé au texte du fragment (`sanitizeEditText` des deux côtés) : égaux, `pasteFragment` (une étape d'annulation) ; sinon `insertText`. Un fragment refusé (`RICH_FRAGMENT_INVALID`, `RICH_LIMIT`) retombe sur le texte. Le menu contextuel suit la même règle (`rememberFragment`, `pasteText`). Pas de glisser de texte vers un autre onglet.
* **Moteur perdu** (4) : première erreur `RICH_UNKNOWN_DOCUMENT` ou `EDITOR_ENGINE_FAILED` : tous les onglets passent à « perdu » (marque d'erreur, saisie coupée, bandeau `role="alert"`). Par onglet : « Rouvrir depuis le fichier… » (boîte d'ouverture, même identifiant, le front ne garde pas de chemin), « Copier le texte affiché » (`editor.windowText`, au plus 256 Kio autour du focus), « Remplacer par un document vierge ». Il n'y a pas de récupération automatique dans l'application (le dernier enregistrement de récupération n'existe pas encore). Worker mort (erreurs `Worker*Error`) : « Copier le texte affiché » reste disponible ; « Relancer le moteur » crée un nouveau Worker et un nouveau transport et ne reconstruit QUE les documents en texte brut (TXT) modifiés dont le texte complet est connu du cache JS (`editor.completeText()`), dans un nouvel éditeur toujours modifié. Un document riche (DOCX, Nouveau riche, modèle : gras, titres, listes, bordures ne laissent aucune trace dans le texte, un enregistrement écraserait le fichier avec du texte nu) et un onglet propre (jamais rendu « modifié ») restent affichés, marqués perdus, lisibles et copiables ; ils se rouvrent depuis leur fichier par la boîte d'ouverture ou se remplacent par un document vierge. Fermer ou remplacer un onglet modifié perdu demande une confirmation qui dit que le texte sera perdu. Le trap lui-même n'est pas rejoué dans le test navigateur (le moteur de produit n'a pas de point d'entrée de panique) : il est simulé en fermant les sessions derrière le dos du front, ce qui produit la même erreur `RICH_UNKNOWN_DOCUMENT` ; le Worker mort est simulé par `client.close()`.
* **Fermeture de la FENÊTRE** : inchangée. Le natif n'a qu'un booléen (le OU) et une confirmation globale : avec un ou plusieurs onglets modifiés, il affiche sa question unique ; il ne propose pas d'enregistrer onglet par onglet. Faire autrement demande un message natif « fermeture demandée » vers le front, une boucle d'enregistrement par onglet, puis un accusé vers le natif (avec garde-fou si le front ne répond pas) : non fait dans cette tranche.
* **Lancement** (US-115) : voir `docs/us-115-single-instance.md`.
* **Identité d'un fichier** : le script ne reçoit jamais de chemin complet. Le natif donne une empreinte OPAQUE (FNV-1a 64 bits du chemin canonique en minuscules, `std::fs::canonicalize` : noms 8.3 résolus, casse réelle, préfixe verbatim retiré ; 16 chiffres hexadécimaux). Pour le lancement elle arrive avec le nom du fichier ; pour la boîte d'ouverture et les récents le front la demande à part par `fileIdentity|r<n>` (travail sur un fil de lecture, jamais sur le fil de la fenêtre : un partage injoignable ne fige pas l'interface). Un fichier déjà ouvert affiche son onglet. Enregistrer sous efface l'empreinte de l'onglet.
